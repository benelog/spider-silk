= 생성되는 JSON 코덱
:navtitle: 생성되는 JSON 코덱

``silk-json-processor``는 ``@JsonBound``가 붙은 모든 타입의 ``JsonCodec``을 컴파일 시점에 그 타입 자신의 선언으로부터 생성한다.
코덱은 타입 곁의 상수 ``<Type>Json.CODEC``이며, 핸들러는 손으로 작성한 라이터를 지명하듯 그것을 지명한다.
중첩 타입의 코덱 이름은 그 타입을 감싼 타입들의 이름으로 시작하므로, ``Outer.Inner``는 ``OuterInnerJson``을 생성한다.
제네릭 타입에는 상수가 없고, 타입 인자마다 코덱을 받아 xref:#generics[자신의 코덱을 만든다].
한 패키지의 ``Outer.Inner``와 최상위 ``OuterInner``처럼 코덱 이름이 겹치는 두 타입은 컴파일 에러다.
리플렉션으로 들여다보는 것도, 스스로 등록하는 것도 없으며, 네이티브 이미지에는 그 타입에 대한 항목이 필요 없다.

[source,java]
----
@JsonBound
public record Deck(long id, @JsonbProperty("deck_name") String name, @Nullable String note) {
}
----

[source,java]
----
app.get("/api/decks/{deckId}", req -> WebResponse.json(service.deck(req.pathParamLong("deckId")), DeckJson.CODEC));

app.post("/api/decks", req -> {
    Deck deck = req.bodyJson(DeckJson.CODEC); // no id or deck_name -> 400
    return WebResponse.json(service.create(deck), DeckJson.CODEC).status(HttpStatus.CREATED);
});
----

생성된 클래스는 쓸 때는 레코드의 접근자를, 읽을 때는 정규 생성자를 부르며, 각 키는 ``JsonKey``로 한 번만 인코딩한다.
이 클래스는 빌드 디렉터리 아래의 Java 소스로서 다른 소스처럼 읽을 수 있고, xref:json.adoc#silk-json[silk-json] 외에는 아무것에도 의존하지 않는다.

[#setup]
== 설정

프로세서는 javac 안에서 실행되므로, 빌드는 프로세서를 프로세서 경로에 올리고 ``jakarta.json.bind`` 애너테이션을 컴파일 클래스패스에 더한다:

[source,groovy,subs="attributes+"]
----
dependencies {
    annotationProcessor '{silk-json-group}:silk-json-processor:{project-version}'
    compileOnly 'jakarta.json.bind:jakarta.json.bind-api:3.0.4'
}
----

xref:gradle-plugin.adoc#json[Gradle 플러그인]은 ``spiderSilk { json() }``으로 둘 다 더하고, xref:maven-parent.adoc#json[Maven 부모 POM]은 모든 자식의 컴파일러 경로에 프로세서를 올린다.
어느 jar도 런타임에는 필요 없다: 애너테이션은 코덱을 생성할 때 읽히고 다시는 읽히지 않는다.

모듈 경로 위의 애플리케이션은 ``module-info.java``에 ``requires static java.compiler;``와 ``requires static org.jspecify;``를 더한다.
생성된 코드는 ``java.compiler``의 ``@Generated``와 jspecify의 ``@Nullable``을 지니며, 둘 다 런타임에는 필요 없다.
프로세서는 어떤 애너테이션도 차지하지 않으므로, javac의 ``processing`` 린트는 ``@JsonBound``를 아무도 차지하지 않았다고 경고한다.
``@JsonBound``를 차지하면, ``*``를 지원하는 프로세서가 ``@JsonBound``만 있는 라운드에서 실행되지 않게 된다.
차지한다고 린트가 조용해지지도 않는다: 프로세서가 하나라도 실행되면, 린트는 각 코덱에 붙은 ``@Generated``나 JUnit의 ``@Test``처럼 어떤 프로세서도 차지하지 않은 선언 애너테이션마다 경고한다.
``-Werror``로 컴파일하는 빌드는 ``-Xlint:all,-processing``으로 그 린트를 끈다.

== 애너테이션

어휘는 Jakarta JSON Binding의 것이므로, 다른 JSON-B 구현을 위해 애너테이션을 붙인 타입은 그 애너테이션을 그대로 쓴다.
``@JsonBound``는 silk-json 자신의 유일한 애너테이션이며, 코덱을 생성할 타입임을 표시할 뿐이다.

[cols="2,4",options="header"]
|===
| 애너테이션 | 생성된 코덱이 하는 일

| `@JsonbProperty("name")`
| 와이어 위의 멤버 이름을 정한다.
없으면 이름은 컴포넌트, 필드, 프로퍼티의 이름이다.

| `@JsonbTransient`
| 양방향 모두에서 프로퍼티를 뺀다.
이렇게 표시된 레코드 컴포넌트에는 코덱이 null을 건네므로, 원시 타입일 수 없다.

| `@JsonbNillable`
| 패키지나 타입 전체, 또는 프로퍼티 하나에서 null 값을 ``null``로 쓴다.
없으면 null인 프로퍼티는 문서에서 빠진다.

| `@JsonbPropertyOrder({...})`
| 지명한 프로퍼티를 그 순서대로 먼저 쓰고, 나머지는 선언 순서대로 쓴다.

| `@JsonbCreator`
| 클래스를 만드는 생성자나 정적 팩토리 메서드를 표시하며, 각 파라미터가 프로퍼티다.
파라미터는 ``@JsonbProperty`` 이름으로, 그것이 없으면 Java 이름으로 프로퍼티와 짝지어진다.
코덱이 생성자나 메서드를 부르므로, 그것은 private이 아니다.

| `@JsonbDateFormat("pattern", locale = "...")`
| 패키지나 타입 전체, 또는 프로퍼티 하나에서 ``java.time`` 값을 ISO-8601 텍스트 대신 그 패턴으로 포맷하고 파싱한다.
패턴은 컬렉션의 원소, 맵의 값, ``Optional``의 값에도 적용된다.
``Instant``는 UTC로 포맷된다.
``JsonbDateFormat.TIME_IN_MILLIS``는 에포크 이후의 밀리초를 JSON 숫자로 쓰고 읽는다.
이것은 `Instant`, `ZonedDateTime`, `OffsetDateTime`, `LocalDateTime`, ``LocalDate``를 받으며, 그 밖의 타입은 컴파일 에러다.
이렇게 읽은 값은 UTC에 있고, ``LocalDateTime``과 ``LocalDate``는 UTC 기준으로 다룬다.

| `@JsonbNumberFormat("pattern", locale = "...")`
| 패키지나 타입 전체, 또는 프로퍼티 하나에서 숫자를 그 ``DecimalFormat`` 패턴의 문자열로 쓰고 읽는다.
패턴은 컬렉션의 원소, 맵의 값, ``Optional``의 값에도 적용된다.
JDK가 거부하는 패턴은 컴파일 에러이며, 빈 패턴은 숫자를 그대로 둔다.
로캘이 없으면 기호는 ``Locale.ROOT``의 것이므로, 와이어 형식은 JVM의 기본 로캘에 따라 바뀌지 않는다.
문자열은 통째로 읽으며, 패턴의 숫자가 아닌 문자열, 정수 타입에 온 소수, 범위를 벗어난 숫자는 ``JsonException``이다.
네이티브 이미지는 빌드가 ``-H:IncludeLocales``로 포함한 로캘만 가진다.

| `@JsonbTypeAdapter(MyAdapter.class)`
| 프로퍼티나 타입에서, ``new``로 만든 ``JsonbAdapter<Original, Adapted>``를 통해 값을 변환한다.
어댑터에는 공개 무인자 생성자가 필요하며, 프로세서가 이를 검사한다.
타입에 붙으면 그 타입이 쓰이는 모든 곳에서 값 전체를 변환하므로, 인터페이스나 추상 클래스도 바인딩할 수 있다.

| `@JsonbTypeSerializer(MySerializer.class)`, `@JsonbTypeDeserializer(MyDeserializer.class)`
| 프로퍼티나 타입에서, ``new``로 만든 ``JsonbSerializer``나 ``JsonbDeserializer``에 값을 넘긴다.
그 클래스에는 공개 무인자 생성자가 필요하며, 빌드에는 이를 실행하는 xref:jsonb.adoc#serializers[`silk-json-jsonb`]가 필요하다.

| `@JsonbTypeInfo({...})`
| xref:#subtypes[하위 타입]에서 설명하듯이, 타입의 하위 타입을 와이어 위의 별칭과 함께 나열한다.
|===

``@JsonbVisibility``는 지원하지 않으며, ``PropertyVisibilityStrategy``가 ``java.lang.reflect.Field``와 ``java.lang.reflect.Method``를 받으므로 타입이나 패키지에 붙으면 컴파일 에러다.
기본 순서는 선언 순서이며, JSON-B 자체의 기본값은 사전순이다.

== 타입의 모양

레코드는 컴포넌트와 정규 생성자를 통해 바인딩된다.
클래스는 공개 getter, setter, 공개 필드를 통해 바인딩되고, ``@JsonbCreator``나 공개 무인자 생성자를 통해 만들어진다.
클래스가 상속한 멤버도 바인딩되며, 상위 클래스의 프로퍼티가 먼저 오고, 클래스가 오버라이드한 멤버는 클래스의 애너테이션으로 읽힌다.
이름이 ``is``로 시작하는 getter는 ``boolean``이나 ``Boolean``을 반환한다.
한 프로퍼티의 getter와 setter는 같은 타입을 다루며, 어긋나면 컴파일 에러다.
setter나 필드를 통해 설정되는 프로퍼티는 문서에 없으면 클래스 자신의 기본값을 유지한다.
코덱은 타입을 지명하고 그 생성자를 부르므로, 중첩 클래스는 static이며, 타입도, 그것을 감싼 타입도, 코덱이 부르는 생성자도 private이 아니다.

코덱이 아는 프로퍼티 타입은 원시 타입과 그 박싱 타입, `String`, `BigDecimal`, `BigInteger`, `UUID`, `URI`, 한 번만 인코딩한 상수 이름으로 쓰고 읽는 enum, ISO-8601 텍스트로 쓰이는 ``java.time`` 타입, `Optional`, `OptionalInt`, `OptionalLong`, `OptionalDouble`, `List`, `Set`, `Collection`, `Iterable`, `Map<String, V>`, ``JsonValue`` 트리, ``@JsonBound``가 붙은 다른 모든 타입, 그리고 제네릭 타입 안에서는 그 타입 변수다.
컬렉션의 원소와 맵의 값도 같은 타입들이며, 필요한 만큼 깊이 중첩된다.
그 밖의 타입은 프로퍼티를 지목하는 컴파일 에러이며, 해결 방법은 둘이다: 그 타입에 ``@JsonBound``를 붙이거나, ``@JsonbTypeAdapter``로 변환한다.

== 필수와 선택

읽을 때 레코드 컴포넌트나 생성자 파라미터는 그 타입이 값이 없을 수 있음을 나타내지 않는 한 필수다.
어느 라이브러리의 것이든 ``@Nullable``이 붙은 타입은 없거나 null인 멤버를 null로 읽는다.
이 애너테이션은 레코드 컴포넌트, 생성자 파라미터, 필드, 접근자 어디에 붙어도 효력이 있다.
``Optional``은 그런 멤버를 비어 있는 것으로 읽는다.
그 밖의 컴포넌트가 문서에 없거나 ``null``로 있으면 ``JsonException``이며, ``req.bodyJson(codec)``는 이에 400으로 답하는데, 이는 ``pathParamLong``과 같은 계약이다.
타입에 없는 멤버는 건너뛴다.

이는 없는 프로퍼티를 기본값으로 두는 JSON-B 자체의 기본 동작보다 엄격하며, 이 엄격함은 의도한 것이다: 핸들러는 값 전체를 받거나 아무것도 받지 않는다.

[#generics]
== 제네릭 타입

제네릭 타입의 코덱은 타입 변수마다 코덱을 받으므로, ``CODEC`` 상수가 없는 클래스다.
``PageJson.of(...)``가 이를 만들고, 결과는 상수에 둔다:

[source,java]
----
@JsonBound
public record Page<T>(List<T> items, @Nullable String next) {
}

static final JsonCodec<Page<Deck>> DECK_PAGE = PageJson.of(DeckJson.CODEC);
----

``Page<Deck> decks``처럼 타입 인자를 지명한 프로퍼티에는 상수가 필요 없다.
그 코덱은 값을 읽거나 쓰는 자리에서 만들어지며, 인자는 ``Page<String>``이나 ``Page<List<Deck>>``처럼 코덱이 아는 어떤 타입이든 된다.
상수는 두 코덱의 정적 초기화를 묶어 두 스레드가 서로를 기다리게 할 수 있으므로, 빌드는 이를 상수에 두지 않는다.
``Node<T>`` 안의 ``Node<T> next``처럼 자신의 인자로 자신을 가리키는 타입은 지금의 코덱을 쓴다.
타입 변수의 경계는 코덱에도 그대로 붙는다.

[#subtypes]
== 하위 타입

``@JsonbTypeInfo``는 인터페이스나 추상 클래스를, 와이어 위의 별칭을 가진 나열된 하위 타입에 바인딩한다.

[source,java]
----
@JsonBound
@JsonbTypeInfo({
    @JsonbSubtype(alias = "dog", type = Dog.class),
    @JsonbSubtype(alias = "cat", type = Cat.class)
})
public sealed interface Animal permits Dog, Cat {
}

@JsonBound
public record Dog(String name) implements Animal {
}

@JsonBound
public record Cat(int lives) implements Animal {
}
----

``AnimalJson.CODEC``은 ``Cat``을 ``{"@type":"cat","lives":9}``로, 즉 키를 먼저 쓰고 하위 타입의 멤버를 이어 쓴다.
키는 ``key = "..."``가 다른 이름을 정하지 않으면 ``@type``이다.
코덱은 ``instanceof``로 하위 타입을 고르며, 하위 클래스를 상위 클래스보다 먼저 시도한다.
나열된 하위 타입 어디에도 속하지 않는 값은 ``IllegalArgumentException``이다.

읽을 때는 객체의 어느 자리에 있든 키를 찾고, 그다음 하위 타입의 코덱이 객체를 읽는다.
키가 없거나 타입이 나열하지 않은 별칭을 가진 객체는 ``JsonException``이다.

하위 타입 자신의 코덱은 키를 쓰지 않는다: ``CatJson.CODEC``은 ``{"lives":9}``를 쓴다.
이는 하위 타입을 자신의 타입으로 쓰든 상위 타입으로 쓰든 키를 쓰는 Yasson과 다르다.
자신의 하위 타입을 나열한 하위 타입은 자신의 키를 가지며, 문서에는 두 키가 모두 들어간다.

추상 클래스가 아닌 클래스에도 ``@JsonbTypeInfo``를 붙일 수 있다.
이때 코덱은 그 클래스 자체의 값을 키 없이 쓰고, 키가 없는 객체를 그 클래스 자체로 읽는다.

프로세서는 동작하지 않을 것을 각각 컴파일 에러로 거부한다:

* ``@JsonBound``가 없거나, 제네릭이거나, 시리얼라이저나 어댑터가 통째로 쓰는 하위 타입
* 두 번 나열된 별칭, 또는 하위 타입이 없는 목록
* 부모의 키와 같은 하위 타입의 키
* JSON 이름이 키와 같은 프로퍼티
* 제네릭 타입이나 값 전체의 변환과 함께 쓴 ``@JsonbTypeInfo``

[#mixin]
== 소유하지 않은 타입 바인딩하기

도메인 레코드나 다른 라이브러리의 타입처럼 애너테이션을 지닐 수 없는 타입은 믹스인을 통해 바인딩한다: ``@JsonBound(Other.class)``가 붙은 타입으로, 같은 이름의 멤버들이 ``Other``의 프로퍼티를 위한 애너테이션을 지닌다.
코덱은 믹스인 곁의 그 패키지에 ``OtherJson``으로 생성된다.
레코드에서 믹스인의 메서드는 같은 이름의 컴포넌트를 가리키므로, ``isAdmin()``은 컴포넌트 ``isAdmin``이다.
클래스에서 믹스인의 메서드는 그 JavaBeans 이름이 가리키는 프로퍼티를 가리킨다.

[source,java]
----
@JsonBound(DeckSummary.class)
interface DeckSummaryWire {
    @JsonbProperty("card_count") long cardCount();
}

static final JsonCodec<DeckSummary> DECK_SUMMARY = DeckSummaryJson.CODEC;
----

xref:example-flashcard.adoc[예제 애플리케이션]은 ``DeckSummary``를 이렇게 바인딩한다: 도메인 레코드에는 애너테이션이 없고, 와이어 포맷은 웹 계층에서 정한다.

[#names]
== 와이어 포맷과 이름 바꾸기

프로퍼티의 와이어 위 이름은 ``@JsonbProperty``가 달리 말하지 않는 한 Java 이름이므로, 컴포넌트 이름을 바꾸면 멤버 이름도 바뀐다.
손으로 작성한 라이터는 누군가 고칠 때만 와이어 포맷이 바뀌며, xref:reflection-scope.adoc[리플렉션 없음 장]은 그 성질이 왜 중요한지 밝힌다.
모든 이름을 적어 두길 원하는 빌드는 프로세서에 ``-Asilkjson.names=explicit`` 옵션을 넘기며, 그러면 ``@JsonbProperty`` 이름이 없는 프로퍼티는 컴파일 에러가 된다:

[source,groovy]
----
tasks.withType(JavaCompile).configureEach {
    options.compilerArgs.add('-Asilkjson.names=explicit')
}
----
