= Undertow
:navtitle: Undertow

`spider-silk-undertow`는 같은 앱을 임베디드 Undertow에서 실행한다.
이 모듈이 따로 있는 이유는 `spider-silk-tomcat`과 같다: 특정 서버에 대한 종속은 core의 플래그 뒤가 아니라 아티팩트의 이름에 드러나야 한다.

세 서버의 비교와 선택 기준은 xref:server.adoc#choosing[서버 고르기]를 참고한다.

== 설치

[source,groovy,subs="attributes+"]
----
dependencies {
    implementation('{project-group}:spider-silk-undertow:{project-version}') {
        exclude group: 'org.eclipse.jetty.ee10'    // core's Jetty, unused here
    }
}
----

이 모듈은 Jakarta EE 10 계열인 `undertow-servlet` 2.3.x에 의존한다.
`undertow-servlet` 2.3.x는 Servlet 6.0으로, core의 서블릿 API 및 Jetty의 `ee10`과 같은 수준이다.
Tomcat 11.0.x는 한 단계 위인 Servlet 6.1이다.
`undertow-core`에는 2.4.x가 있지만, 이 모듈에 필요한 절반인 `undertow-servlet`은 아직 2.4.x를 따라가지 않았다.

== 실행

[source,java]
----
new App()
        .get("/hello/{name}", req -> WebResponse.text("Hello " + req.pathParam("name")))
        .server((app, port) -> new UndertowServer(app).port(port))
        .start(8080);
----

`UndertowServer`의 API는 `JettyServer`와 `TomcatServer`를 그대로 따른다:

[source,java]
----
new UndertowServer(app)
        .port(8443)
        .host("127.0.0.1")
        .contextPath("/app")
        .executor(Executors.newVirtualThreadPerTaskExecutor())
        .multipart(new MultipartConfigElement(tmp, 10_485_760L, 10_485_760L, 1_048_576))
        .stopTimeout(Duration.ofSeconds(20))
        .shutdownHook(false)
        .customizeDeployment(deployment -> deployment.setDefaultEncoding("UTF-8"))
        .customizeBuilder(builder -> builder.setIoThreads(4).setWorkerThreads(64))
        .start();
----

커스터마이저가 셋이 아니라 둘인 이유는 Undertow에 접근할 가치가 있는 객체가 둘뿐이기 때문이다: 서블릿 배포를 기술하는 `DeploymentInfo`와 서버를 기술하는 `Undertow.Builder`이다.

== Undertow만의 것

셋 중 Undertow가 가장 쉬운 부분은 정상 종료(graceful shutdown) 하나뿐이다.
`GracefulShutdownHandler`는 자신이 통과시킨 요청을 세므로, `stopTimeout(...)`은 스레드 풀이 비워지기를 기다리지 않고 그 수가 0이 되기를 기다린다.
드레인이 요청을 세기 때문에, Tomcat에서와 달리 `executor(...)`가 드레인을 방해하지 않는다: 가상 스레드 실행기로 교체해도 드레인은 온전히 동작한다.

Undertow의 워커 스레드는 스스로 JVM을 붙들어 두지 않으므로, `start()`는 `stop()`이 풀어 주는 비데몬 스레드를 하나 대기시킨다.
Tomcat 모듈에도 같은 비데몬 스레드가 필요하며, `join()`은 이 스레드를 기다린다.

`sessions(boolean)`은 없다: Undertow 배포는 항상 세션 매니저를 얻는다.
조용히 아무것도 하지 않는 메서드는 메서드가 없는 것보다 나쁘다.
정적 파일은 클래스패스 루트든 디렉터리든 여전히 core 자체의 `StaticFiles`가 제공하므로, Undertow의 리소스 매니저는 의도적으로 비워 둔다.

로깅은 JBoss Logging을 거치며, JBoss Logging은 클래스패스에 slf4j가 있으면 slf4j를 쓴다.
따라서 이미 slf4j를 쓰는 애플리케이션은 브리지 없이 Undertow의 로그를 받는다.
