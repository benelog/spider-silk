= Spider Silk
:navtitle: 소개

image::logo.svg[Spider Silk,160]

호출 스택은 얇게, 시그니처는 탄탄하게.

Spider Silk는 Jakarta Servlet API 위에 만들어진 웹 프레임워크다.

== 추구하는 가치

=== 빠른 부팅 시간
Spider Silk 애플리케이션은 시작하는 데 시간을 거의 쓰지 않는다.
시작 시점에 스캔할 클래스패스도, 만들어 낼 프록시도 없으므로, 부팅 비용은 애플리케이션이 생성자를 호출해 객체를 조립하고 라우트를 등록하는 코드 그 자체다.
부팅 시간은 오토스케일링되는 컨테이너, 서버리스 환경, 테스트마다 서버를 띄우는 테스트 스위트에서 곧바로 비용이 된다.
예제 애플리케이션을 xref:native-image.adoc[GraalVM 네이티브 이미지]로 빌드하면 프로세스가 뜬 뒤 약 55ms 만에 시작 로그를 남기며, 같은 앱을 JVM에서 돌리면 약 1.2초다.

=== 명확한 코드 추적성
요청이 어떤 코드를 거쳐 응답이 되는지는 코드를 읽는 것만으로 따라갈 수 있어야 한다.
이 추적성은 사람 개발자와 AI 코딩 에이전트 모두를 위한 것이다.
사람은 코드를 따라 읽거나 스택 트레이스를 보고 문제가 생긴 지점을 찾는다.
AI 에이전트는 실행해 보기 전에 코드만 읽고 동작을 추론하므로, 코드에 보이지 않는 동작은 추측으로 메울 수밖에 없다.
애너테이션이 실행 시점에 무엇을 하는지, 어떤 프록시가 끼어드는지를 잘못 추측한 에이전트는 그럴듯하지만 동작하지 않는 코드를 쓴다.
그래서 추적성은 AI 에이전트가 만드는 코드의 생산성과 안정성을 좌우하는 요소다.
Spider Silk에서는 라우트 등록부터 핸들러 호출까지 모두 평범한 메서드 호출이다.
`app.routes()`와 `app.hooks()`는 등록된 라우트와 필터를 데이터로 돌려주므로, 어떤 코드가 어떤 요청에 실행되는지 시작 코드를 읽지 않고도 확인할 수 있다.

=== 오픈소스 기술 생태계와의 조화
Spider Silk는 검증된 오픈소스 기술을 새로 만들지 않고 그대로 활용하며, 그 사이의 선택은 사용자에게 맡긴다.
기반은 Jakarta Servlet API이므로, 프레임워크의 서블릿인 `AppServlet`은 어느 서블릿 컨테이너에서나 실행된다.
웹 서버는 Jetty, Tomcat, Undertow 중에서, 템플릿 엔진은 jte, FreeMarker, Handlebars, Thymeleaf 중에서 고른다.
JSON은 core의 손으로 작성하는 API를 기본으로 쓰되, 필요하면 xref:json-interop.adoc[외부 JSON 바인딩]으로 애플리케이션이 고른 라이브러리를 연결한다.
데이터 계층은 프레임워크의 범위 밖이므로, 애플리케이션이 원하는 라이브러리를 고른다.
예제 애플리케이션은 spring-jdbc와 H2를 쓴다.
프레임워크는 이 기술들을 자신의 추상화 뒤에 감추지 않는다.
예를 들어 서버의 커스터마이저는 실제 Jetty 객체를 그대로 건넨다.

== 가치를 위한 기술 선택

=== 리플렉션 없음
애너테이션 스캔도, 프록시도, 자동 바인딩도, 보이는 코드 외의 숨겨진 마법도 없다.
코드를 따라 읽는 대로 실행되고, 스택 트레이스는 짧고, 애플리케이션의 부팅은 빠르다.
결과적으로 GraalVM 네이티브 이미지 친화적이 되었다.

=== 최소한의 콜 스택 추가

이 프레임워크는 주된 호출 경로에서 `HttpServlet.service` 위에 2개의 스택 프레임만을 추가한다.

[source,text]
----
java.lang.Throwable: where a handler stands
    at com.example.decks.DeckRoutes.one(DeckRoutes.java:15)  // the handler
    at net.benelog.spidersilk.AppServlet.dispatch(AppServlet.java:221)  // Spider Silk
    at net.benelog.spidersilk.AppServlet.service(AppServlet.java:128)  // Spider Silk
    at jakarta.servlet.http.HttpServlet.service(HttpServlet.java)  // the Servlet API
    at org.eclipse.jetty.ee10.servlet.ServletHolder.handle(ServletHolder.java)  // Jetty, from here down
----

프레임워크의 어떤 지점도 네 프레임보다 깊지 않다.

=== API의 단순성, 직관성 추구
프레임워크의 핵심 API는 단순하고 명확하다.
핸들러는 HTTP 요청을 받아서 응답으로 변환하는 함수다.
요청은 `WebRequest` 타입의 메서드 파라미터로, 응답은 `WebResponse` 타입으로 반환한다.

[source, java]
.Handler interface
----
@FunctionalInterface
public interface Handler {
    WebResponse handle(WebRequest request) throws Exception;
}
----

`Handler` 인터페이스에 맞춰 람다 표현식이나 메서드 레퍼런스로 URL 라우팅 정책을 정의할 수 있다.

[source,java]
.Handler와 URL 라우팅 매핑
----
var deckRepository = new DeckRepository(dataSource);
var deckService = new DeckService(deckRepository);
var app = new App();

app.get("/decks/{deckId}", req -> {
    long deckId = req.pathParamLong("deckId");
    Deck deck = deckService.getDeck(deckId);
    return WebResponse.template("deck", Map.of("deck", deck));
});

app.get("/api/decks", req -> {
    JsonArray resBody = Json.array();
    for (DeckSummary deck : deckService.deckSummaries()) {
        resBody.add(Json.object()
            .put("id", deck.id())
            .put("name", deck.name()));
    }
    return WebResponse.json(resBody);
});

app.post("/api/decks", req -> {
    String name = req.bodyJson(json -> json.asObject().getString("name"));
    Deck deck = deckService.createDeck(name);
    JsonObject resBody = Json.object()
        .put("id", deck.id())
        .put("name", deck.name());
    return WebResponse.json(resBody).status(HttpStatus.CREATED);
});

app.start(8080);                                //
----

=== 추구하는 가치에 맞는 디폴트 기술 스택
`spider-silk-core`는 웹 서버로 Jetty를, 템플릿 엔진으로 jte를 기본으로 담고 있다.
의존성 하나만 추가하면 서버와 템플릿 엔진을 갖춘 애플리케이션을 바로 시작할 수 있다.

==== Jetty
기본 웹 서버는 임베디드 Jetty다.
정상 종료, 셧다운 훅, JVM 유지는 세 서버 모두에서 동작한다.
Jetty는 이를 자체 기능으로 제공하고, Tomcat과 Undertow에서는 이 프레임워크가 직접 구현해서 붙인다.
그래서 Jetty를 쓸 때 애플리케이션과 서버 사이에 놓이는 이 프레임워크의 코드가 가장 적다.
Jetty에서는 정상 종료를 Jetty 자체의 `stopTimeout`이, 셧다운 훅을 `setStopAtShutdown`이, JVM 유지를 Jetty의 non-daemon 스레드가 맡는다.
Jetty는 디스크 위의 작업 디렉터리 없이 실행된다.
세션은 `sessions(false)`로 끌 수 있으며, 세 서버 중 세션을 끌 수 있는 것은 Jetty뿐이다.
자주 조정하는 설정은 `JettyServer`의 메서드로 바꾸고, 그 밖의 설정은 커스터마이저가 실제 Jetty 객체에 직접 접근해서 바꾼다.
세 서버의 비교는 xref:server.adoc#choosing[서버 고르기]에 있다.

==== jte
기본 템플릿 엔진은 https://jte.gg[jte]다.
jte는 템플릿을 Java 소스로 컴파일한다.
리플렉션이 없고 직관적이고 단순한 프레임워크의 원칙과 잘 맞는다.
미리 컴파일한 템플릿은 런타임에 컴파일러가 필요 없으므로 xref:native-image.adoc[GraalVM 네이티브 이미지]에서도 동작한다.
개발 중에는 템플릿을 고치면 다시 빌드하지 않아도 바로 반영된다.

jte를 고르면서 감수한 비용도 있다.
`Map`이나 `Model.of`로 넘기는 모델은 Java 컴파일러가 검사하지 않으므로, 키 이름이나 타입이 틀리면 페이지를 렌더링할 때에야 드러난다.
템플릿 안에 임의의 Java 식을 쓸 수 있으므로, 로직이 템플릿으로 새어 나가지 않게 하는 것은 애플리케이션의 몫이다.
JStachio처럼 템플릿을 모델 클래스에 묶는 엔진과의 비교는 https://github.com/benelog/spider-silk/blob/main/notes/decisions.md[notes/decisions.md]의 결정 72에 있다.

=== 확장성 있는 모듈 구조
기본 기술 스택은 선택 모듈로 바꿀 수 있고, core에 없는 기능은 선택 모듈로 더한다.
모든 모듈은 `spider-silk-core`에 의존하고, core는 어느 모듈에도 의존하지 않는다.
모듈은 묶여 있는 대상의 이름을 따르므로, 특정 서버나 엔진에 대한 종속은 core의 플래그가 아니라 아티팩트의 이름에 드러난다.

.웹 서버
* xref:tomcat.adoc[`spider-silk-tomcat`]은 같은 앱을 임베디드 Tomcat에서 실행한다.
Tomcat을 이미 운영하는 조직이나 Spring Boot에서 옮겨 오는 애플리케이션에 맞는다.
* xref:undertow.adoc[`spider-silk-undertow`]는 같은 앱을 임베디드 Undertow에서 실행한다.
Undertow의 정상 종료는 요청을 세므로, 가상 스레드 executor에서도 드레인이 동작한다.

라우팅, 필터, 상태 페이지, JSON, 템플릿, 정적 파일, SSE, 멀티파트 업로드, 세션은 세 서버에서 같게 동작한다.
`TomcatServer`와 `UndertowServer`의 API는 `JettyServer`를 그대로 따르므로, 서버를 바꾸려면 `App.server(...)`에 넘기는 팩토리 한 줄만 고치면 된다.

.템플릿 엔진
* xref:freemarker.adoc[`spider-silk-freemarker`]는 https://freemarker.apache.org[FreeMarker]로 렌더링한다.
* xref:handlebars.adoc[`spider-silk-handlebars`]는 https://github.com/jknack/handlebars.java[Handlebars.java]로 렌더링한다.
* xref:thymeleaf.adoc[`spider-silk-thymeleaf`]는 https://www.thymeleaf.org[Thymeleaf]로 렌더링한다.

엔진은 `App.templates(...)`로 바꾸며, 핸들러의 `WebResponse.template(name, model)`은 엔진과 관계없이 그대로다.

.WebSocket
* xref:websocket.adoc[`spider-silk-jetty-websocket`]은 앱의 HTTP 라우트 곁에 WebSocket 엔드포인트를 매핑한다.
구조상 Jetty 전용이므로, `App`의 메서드가 아니라 Jetty의 이름을 단 모듈이다.

=== 개발도구 생태계 연동
테스트, API 문서, 빌드, AI 코딩 에이전트를 위한 도구는 별도 모듈과 스킬로 제공된다.

.테스트
* xref:testing.adoc[`spider-silk-test`]의 `WebTest` 하니스는 빈 포트에서 앱을 시작하고, 쿠키를 유지하는 클라이언트를 건넨다.
별도 모듈이므로 프로덕션 jar에는 테스트 코드가 실리지 않는다.

.API 문서
* xref:openapi.adoc[`spider-silk-openapi`]는 `app.routes()`가 돌려주는 라우트 목록을 OpenAPI 3.1 문서로 바꾼다.
라우트가 평범한 데이터이므로, 이 모듈은 리플렉션 없이 동작한다.

.빌드 도구
* xref:gradle-plugin.adoc[Gradle 플러그인] `net.benelog.spidersilk`는 jte 템플릿 사전 컴파일, Jib 컨테이너 이미지, GraalVM 네이티브 컴파일의 컨벤션을 담는다.
* xref:maven-parent.adoc[`spider-silk-maven-parent`]는 같은 패키징 컨벤션을 Maven의 부모 POM으로 제공한다.

.AI 코딩 에이전트
* xref:agent-skill.adoc[에이전트 스킬]은 `skills/spider-silk/`에 https://agentskills.io[Agent Skills] 형식으로 들어 있으며, 에이전트가 프레임워크를 추측하지 않고 의도대로 쓰도록 안내한다.
Agent Skills는 개방 표준이고 이 스킬은 특정 도구에만 있는 기능을 쓰지 않으므로, 같은 디렉터리를 Claude Code, Codex, Cursor, GitHub Copilot 등 여러 AI 에이전트가 그대로 읽는다.
리포지토리가 플러그인 마켓플레이스를 겸하므로, Claude Code에서는 두 명령으로 설치한다.
