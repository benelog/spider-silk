= External JSON Binding
:navtitle: External JSON Binding

An application can bind JSON with a library of its own, through a seam of two methods that were always there.
Core's JSON is hand-written on purpose, but that decision is the framework's to make for core, not for the application.
An application with three hundred DTOs, or one whose wire format is generated from a schema it does not own, has a reason to bind objects with a library.

== The seam

Going out, `WebResponse.json(String rawJson)` takes a document that is already serialized.
Coming in, `req.bodyStream()` and `req.bodyReader()` hand over the body unread.

[source,java]
----
public static WebResponse json(String rawJson)   // whatever produced it
public InputStream bodyStream()                  // the bytes, unparsed
public BufferedReader bodyReader()               // the characters, unparsed
----

That is the whole integration.
Do not route another library's output through `JsonWriter<T>`: it returns a `Json.JsonValue`, which would mean re-parsing a document the library had just finished writing.
The library serializes, and `json(String)` sends what it produced.

The servlet API allows a body to be read as bytes or as characters, not both.
A request that has already been through `body()`, `bodyJson()`, `bodyNdjson()`, or `param()` throws `IllegalStateException` from `bodyStream()`, because all four read characters.
The reverse holds as well.
Whichever a handler picks, it picks once.

== Jackson

[source,java]
----
static final ObjectMapper MAPPER = new ObjectMapper();

app.get("/api/decks", req -> {
    try {
        return WebResponse.json(MAPPER.writeValueAsString(deckService.decks()));
    } catch (JsonProcessingException e) {
        throw new IllegalStateException(e);
    }
});

app.post("/api/decks", req -> {
    NewDeck body;
    try (InputStream in = req.bodyStream()) {
        body = MAPPER.readValue(in, NewDeck.class);
    } catch (IOException e) {
        throw new HttpException(HttpStatus.BAD_REQUEST, "Malformed JSON body");
    }
    return WebResponse.json(MAPPER.writeValueAsString(deckService.create(body.name())));
});
----

Read through `bodyStream()` rather than `body()` on the way in.
Jackson then parses the socket, and the request never exists as one String.

Move the two `try` blocks into an `exception(JsonProcessingException.class, ...)` handler on the `App` once there is more than one handler.

== Gson

[source,java]
----
static final Gson GSON = new Gson();

app.get("/api/decks", req -> WebResponse.json(GSON.toJson(deckService.decks())));

app.post("/api/decks", req -> {
    NewDeck body = GSON.fromJson(req.bodyReader(), NewDeck.class);
    return WebResponse.json(GSON.toJson(deckService.create(body.name())));
});
----

Gson reads characters, so `bodyReader()` is its half of the seam.
`fromJson` returns null for an empty body and throws `JsonSyntaxException` for a malformed one.
Both are the application's to answer, since core has not been told this body is JSON.

== A binder that generates its code

xref:reflection-scope.adoc[The framework's no-reflection rule] is about core, and a library an application adds answers for itself.
Jackson and Gson both read and write fields reflectively, which is a real cost under a xref:native-image.adoc[native image]: every bound type needs a reflection entry.

https://avaje.io/jsonb/[avaje-jsonb] is the version of this that keeps the property:

[source,java]
----
@Json
public record Deck(long id, String name) { }
----

[source,java]
----
static final Jsonb JSONB = Jsonb.builder().build();
static final JsonType<Deck> DECK = JSONB.type(Deck.class);

app.get("/api/decks/{deckId}", req ->
        WebResponse.json(DECK.toJson(deckService.deck(req.pathParamLong("deckId")))));
----

Its annotation processor generates a Java source adapter per type at compile time and registers it through `ServiceLoader`.
There is no reflective fallback.
The runtime therefore stays reflection-free, and the native image needs no entry for a bound type, which is the same trade jte makes for templates.

What it does *not* keep is the stronger promise underneath the no-reflection rule: the wire format changes only when someone edits it.
A generated adapter derives its field names from the record's components, so renaming a component renames a JSON field.
It does so silently, at compile time, in a build that still succeeds.
Pinning each name with `@Json.Property("...")` restores the guarantee, and costs about as much typing as the hand-written writer it replaced.
That is the trade.
Where it comes out is the application's call, and core is not involved either way.

DSL-JSON's `@CompiledJson` works the same way, with one difference worth knowing.
It keeps a runtime reflection fallback for types the processor did not see, so "no reflection" there is a configuration to hold rather than a property of the build.

== What core still does

Routing, parameter extraction, and the request and response envelope are unchanged by any of this.
An application can bind one endpoint with a library and hand-write the next.
`WebResponse.json` takes a `String` and does not ask where it came from.

No module of this project depends on Jackson, Gson, or avaje-jsonb.
