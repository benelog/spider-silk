= Appendix: Performance Benchmark
:navtitle: Appendix: Benchmark

This appendix reports one run of the benchmark in the repository's `benchmark/` directory, which measures Spider Silk against Spring MVC on the same machine, with the same JVM and the same load.
The run took place on 2026-10-09 on the laptop described under <<machine>>, against `main` at commit `fa300ce`, 143 commits after the 1.1.0 release, with the change that has `WebResponse.json` answer with `Bytes` applied on top.

[#summary]
== Summary

The numbers below are medians, and they hold for this machine and these handlers only.

* Plain text and a small JSON object answer about 1.45 times as many requests per second on Spider Silk with Jetty as on Spring MVC.
On the same container, Tomcat, the margin is about 1.25 times.
* A JSON list of 100 records, where the serializer does most of the work, answers 2% to 5% more requests per second on Spider Silk than on Spring MVC with Jackson.
* A page rendered with jte, Spider Silk's default engine, answers about 3.2 times as many requests per second as Spring MVC with Thymeleaf.
With Thymeleaf on both sides, the two are within 5% of each other.
* A JVM process starts in 312 ms on Spider Silk with Jetty and in 923 ms on Spring Boot, and holds 116 MB against 216 MB of resident memory at that point.
* As GraalVM native images, Spider Silk starts in 48 ms and Spring MVC in 50 ms, and building the image takes 89 s and 105 s respectively.
The native images answer fewer requests per second than the JVM in every case, by 23% to 85%.

== What was measured

=== Targets

Five servers were measured, each in a process of its own.

[cols="2,3,3",options="header"]
|===
| Target | Stack | Runtime

| `spider-silk-jetty`
| Spider Silk, embedded Jetty 12.1.13, jte 3.2.4 or Thymeleaf 3.1.5
| JVM

| `spider-silk-tomcat`
| Spider Silk, `spider-silk-tomcat` on embedded Tomcat 11.0.26, jte 3.2.4 or Thymeleaf 3.1.5
| JVM

| `spring-mvc`
| Spring Boot 4.1.1 (Spring Framework 7.0.9), Spring MVC, embedded Tomcat 11.0.24, Jackson 3.1.5, Thymeleaf 3.1.5
| JVM

| `spider-silk-jetty-native`
| the same application as `spider-silk-jetty`
| GraalVM native image

| `spring-mvc-native`
| the same application as `spring-mvc`, AOT-processed
| GraalVM native image
|===

Spring Boot runs with its defaults: no property is set, and Tomcat, Jackson, and Thymeleaf are what the starters bring.
Spider Silk runs with its defaults too, apart from the server and the template engine its arguments pick.
Both servers have a pool of at most 200 platform threads, and neither uses virtual threads.

The native image of Spider Silk was built for Jetty only.

=== Cases

Each case is one `GET` that returns the same body on both frameworks.

[cols="2,1,4,4,1",options="header"]
|===
| Case | Path | Spider Silk | Spring MVC | Body

| `text`
| `/text`
| `WebResponse.text("Hello, World!")`
| `@GetMapping` returning a `String` as `text/plain`
| 13 B

| `json`
| `/json`
| `WebResponse.json(new Message(...), MESSAGE)`, a hand-written `JsonWriter`
| `@RestController` returning a `Message` record, written by Jackson
| 27 B

| `json-list`
| `/items`
| `WebResponse.json(items, ITEMS)`, with `JsonWriter.list`
| `@RestController` returning a `List<Item>`, written by Jackson
| 10,490 B

| `template-jte`
| `/fortunes`
| `WebResponse.template("fortunes", model)`, jte precompiled
| none
| 1,177 B

| `template-thymeleaf`
| `/fortunes`
| `WebResponse.template("fortunes", model)`, `ThymeleafTemplates`
| `@Controller` returning a view name, Spring Boot's Thymeleaf view resolver
| 1,178 B
|===

The `json-list` body is 100 records of five fields each, and the two frameworks send it byte for byte the same.
The `/fortunes` page is a table of the 12 fortunes from the TechEmpower benchmark, one of which needs HTML escaping and one of which is Japanese.
The two Thymeleaf pages are the same template file and render to the same bytes.
The jte page differs in its blank lines, and in leaving `"` and `'` unescaped in text, which HTML allows.
Every value a handler answers with is built once at startup, so a request measures the framework, the serializer, and the renderer, and not the data.

Since that run, the Spider Silk application answers `json` and `json-list` through the codecs generated from its records, and a `json-post` case sends the 100 records of `json-list` as the body of a `POST /items` on both frameworks, so that the parser is measured as the serializer is.
Both wait for the next run of the whole benchmark, and <<json-microbenchmark>> measures the serializer and the parser on their own.

=== Method

`benchmark/run.sh` drives the whole run.

. `native-build.sh` builds each native image three times from a clean project, alternating between the two applications.
. After a minute's pause, `startup.sh` starts each target ten times with three seconds of quiet before each start.
It times the start from before the process launches to the first `200` from `/text`, polling every 10 ms, and reads the process's resident memory at that moment.
. Each case then gets a fresh process: 20 seconds of warm-up, then 30 seconds of measurement, then the process stops.
. A round runs every case once, case by case, each across every target, and three rounds run in turn.
A machine that slows down as it heats up therefore spreads the drift over every target instead of the last one.

Startup is timed apart from the load cases because a process started right after the previous one stopped under full load starts up to half again as slow.

The load is https://github.com/wg/wrk[wrk] 4.1.0 with 4 threads and 64 keep-alive connections over loopback.
The server is pinned to CPUs 0 to 3, the four performance cores, and wrk to CPUs 4 to 7, the four low-power efficiency cores.
Every JVM and every native image gets `-Xms1g -Xmx1g`.
The JVM is Temurin 25 with its default collector, G1.
The native images come from GraalVM CE 25.2.4, whose only collector is the Serial GC.

The reported throughput and each latency percentile are medians of the three rounds, taken separately.
Across the rounds, the throughput of every case stayed within 12% of its median.
The three cases beyond 8% all fell in the second round: `json-list` on `spider-silk-jetty` and `spider-silk-jetty-native`, and `json` on `spring-mvc-native`.
No request failed in the run.

[#json-microbenchmark]
=== The serializer and the parser alone

`benchmark/json-bench` measures the JSON engine with no HTTP around it, on the documents the HTTP cases send: the 100 records of `json-list` and the 27-byte object of `json`.
It also measures 100 places with three numbers each that have a fraction, which no HTTP case sends, and the same 100 records with nothing to escape and with Korean strings.
It ran on 2026-10-10 on the same machine, on AC power with the `performance` platform profile.
It measured the working tree with the generated codecs applied, under JMH 1.37 with two forks of five warm-up and five measured iterations of a second each, pinned to CPUs 0 to 3, with `-Xms1g -Xmx1g`.
Each cell is the average time per operation and the bytes allocated per operation, the latter from JMH's `gc` profiler.

[cols="2,3,>1,>1",options="header"]
|===
| Operation | Through | Time | Allocation

| the `Json.object()` tree, as `JsonWriter.tree` | 8.5 µs | 24.1 KB
| a hand-written `JsonWriter` | 6.2 µs | 11.3 KB
| the generated codec | 4.8 µs | 10.7 KB
| Jackson 3.1 | 11.8 µs | 19.7 KB

| the generated codec | 9.3 µs | 8.5 KB
| Jackson 3.1 | 19.7 µs | 50.1 KB
| fastjson2 2.0.57 | 9.5 µs | 17.6 KB

.3+| Read the 100 places
| the generated codec | 5.4 µs | 11.1 KB
| Jackson 3.1 | 25.7 µs | 59.7 KB
| fastjson2 2.0.57 | 5.2 µs | 11.2 KB
|===

The generated codec writes the list in 41% of Jackson's time and reads it in 26%, with between a third and a half of the allocation, and writes the small object in a sixth of Jackson's time.
The hand-written writer lands between the tree and the codec: it finds each key among the keys the document has already written, where the codec copies the key from a constant.
The codec reads the 10 KB document in the time fastjson2 takes, and writes the small object in 89% of it.
fastjson2 stays ahead writing the 10 KB document, by 5%.
Its lead is in writing the strings, and it is wider where no string needs an escape: 1.26 times on the plain records and 1.25 times on the Korean ones.
fastjson2 reads a `String`'s own bytes through `sun.misc.Unsafe`, which the JDK is retiring and core does not use.
The codec copies a string's characters out with `getChars` and checks them one at a time.
It escapes a quote or a backslash in the same loop that writes the plain characters, and compares each character instead of looking it up in a table.
Before it did, the first quote sent the rest of the string to a slower loop, and the same write took 5.3 µs.
The JIT compiler of JDK 25 does not vectorize a loop that narrows a `char` to a `byte`, so a pass that checks the whole string before writing it measured slower, not faster.
Each place has a latitude with four decimals, a longitude with six, and a rating with one.
The codec reads them in 5% more than fastjson2's time with the same allocation, and in a fifth of Jackson's.
`readDouble` converts a number from its digits, with one multiplication or division for numbers like these.
Before it did, it made a string of each number for `Double.parseDouble`, and the same read took 12.6 µs and 43.9 KB.
Jackson 3 parses a double with its fast parser by default, so turning `USE_FAST_DOUBLE_PARSER` on changed nothing.
The codec writes the places in fastjson2's time with half its allocation, little more than the document itself, and in under half of Jackson's time.
`JsonOutput` lays out a double's shortest decimal straight in its buffer, by the algorithm `Double.toString` uses since JDK 19, and writes the same text.
Before it did, it made a string of each number with `Double.toString` and copied it, and the same write took 16.5 µs and 35.6 KB.
In the HTTP cases the serializer is a share of the request rather than the whole of it, so the next run is expected to move `json-list` by that share and `json` hardly at all, and `json-post` is where the parser's difference shows.

[#reading]
== Reading the results

The `text` and `json` cases measure what a framework adds to a request, since the body is tiny.
On the same container, Tomcat, Spider Silk answers 24% to 25% more requests per second than Spring MVC.
The two differ in the work done per request.
Spider Silk's path from the servlet to the handler is two stack frames, while Spring MVC resolves a handler mapping, argument resolvers, return-value handlers, and message converters on every request.
Jetty adds another 16% to 19% on top.
It is also the only server that kept four cores busy at these 64 connections, while both Tomcat targets stayed at about 300%.

The `json-list` case narrows the gap to 2% to 5%, because a 10 KB document is the serializer's work rather than the framework's.
At that commit, `JsonWriter.list` built the whole document as a tree in memory before writing any of it, while Jackson wrote each field straight to the response.
Spider Silk then wrote the tree once, as UTF-8 into a byte array, and that array was the body.
For a document of this size, the two approaches cost about the same on the JVM.
The tree has since gone: a writer puts each member straight into the output, and <<json-microbenchmark>> measures what that changed.
An application that sends large documents has two other paths: the streaming writer in xref:large-json.adoc[Large JSON and NDJSON], and a binding library such as Jackson through xref:json-interop.adoc[External JSON Binding].
Neither was measured here.

The template cases show the engine outweighing the framework.
jte runs a template as compiled Java, and renders this page about three times as fast as Thymeleaf, which interprets the template and reads the model through an expression language.
With Thymeleaf on both sides, the framework's share is small enough that the two land within 5% of each other.

The native images give up throughput for startup and memory.
They run code compiled ahead of time without the profile a JIT collects, on GraalVM CE's Serial GC instead of G1.
The allocation-heavy cases suffer most: `spring-mvc-native` under `json-list` answers 15% of what the same application does on the JVM, with a p99 of 59 ms.
Thymeleaf is the one case where Spider Silk's native image is slower than Spring's.
The two evaluate Thymeleaf's expressions differently: Spider Silk's module through OGNL, which reads `Fortune` by reflection, and Spring's integration through SpEL.
Oracle GraalVM offers the G1 collector and profile-guided optimization, which aim at part of this cost.
Neither was measured here.

[#limits]
== Limits

* Client and server share one laptop and talk over loopback, so there is no network latency and no network bottleneck.
* The two halves of the CPU differ: the server ran on performance cores and wrk on efficiency cores.
wrk kept up with the fastest case, so the server, not wrk, set the throughput.
* wrk sends the next request on a connection only after the previous response arrives, so its percentiles omit the time a request would have waited behind a slow one (coordinated omission).
The percentiles compare the targets with each other, not with a service-level objective.
* The CPU ran under the `powersave` governor and the `balanced` profile, so its clock rose and fell with load and temperature.
The interleaved rounds spread that drift over every target.
* The handlers do no I/O, so the numbers measure the framework, the serializer, and the template engine only.
An application that waits on a database spends most of a request there, and the differences above shrink accordingly.
* A response from a Jetty target is 26 bytes longer than one from a Tomcat target, mostly for its `Server: Jetty(12.1.13)` header.

[#reproducing]
== Reproducing the run

The `benchmark/` directory holds both applications and the scripts, and its `README.md` lists the settings.
It is a Gradle build of its own that includes the root build, so the Spider Silk side runs the modules of the working tree it sits in.

[source,bash]
----
sudo apt install wrk # or: brew install wrk
sdk install java 25.2.4-graalce # for the native images
GRAALVM_HOME=~/.sdkman/candidates/java/25.2.4-graalce benchmark/run.sh
----

The run writes `benchmark/results/<timestamp>/` with the raw CSV files, the wrk output, each server's log, a sample response of every case, and the description of the machine.
`benchmark/summarize.sh` reduces that directory to the tables above.
The microbenchmark runs on its own, from the `benchmark/` directory:

[source,bash]
----
../gradlew -p json-bench installDist
taskset -c 0-3 json-bench/build/install/json-bench/bin/json-bench -jvmArgs "-Xms1g -Xmx1g" -prof gc
----

Without `GRAALVM_HOME`, the run measures the JVM targets only.
The full run takes about 75 minutes on this machine.
`ROUNDS=1 BUILD_ROUNDS=1 STARTS=3 WARMUP=5s DURATION=10s` gives a rough picture in about 15 minutes.
