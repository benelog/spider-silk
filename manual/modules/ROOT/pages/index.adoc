= Spider Silk
:navtitle: Introduction

image::logo.svg[Spider Silk,160]

Thin call stack, strong signature.

Spider Silk is a web framework built on the Jakarta Servlet API.

== Values

=== Fast startup
An application's startup time is kept to a minimum.
Startup is a cost paid again at every main point of development and operation: autoscaled containers, serverless environments, test runs, and development-server restarts.

=== Traceable code
The code a request passes through on its way to a response can be followed by reading the source alone.
Human developers and AI coding agents both need that traceability.
For a person, code that is easy to trace is code that is easy to understand and debug.
An AI agent reasons about behavior from the code before running it, so it fills behavior the code does not show with a guess.
An agent that guesses wrong about what an annotation does at runtime, for example, writes code that compiles and does not work.

=== Harmony with the open-source ecosystem
Spider Silk uses proven open-source technology instead of reinventing it.
Where several technologies play the same role, it leaves an extension point open for the user to choose one.

== Design and technology choices
This section describes the design and the technology the framework chose to realize the three values above.

=== A simple, intuitive API
Spider Silk keeps its core API intuitive and simple, for traceability.
A handler, the core interface, receives the HTTP request as a method parameter of type `WebRequest` and returns the response as a `WebResponse`.

[source,java]
.The Handler interface
----
@FunctionalInterface
public interface Handler {
    WebResponse handle(WebRequest request) throws Exception;
}
----

A handler is mapped to a URL and an HTTP method as a lambda expression or a method reference.

[source,java]
.Registering routes
----
var deckRepository = new DeckRepository(dataSource);
var deckService = new DeckService(deckRepository);
var app = new App();

app.get("/decks/{deckId}", req -> {
    long deckId = req.pathParamLong("deckId");
    Deck deck = deckService.getDeck(deckId);
    return WebResponse.template("deck", Model.of("deck", deck));
});

app.get("/api/decks", req -> {
    JsonArray resBody = Json.array();
    for (DeckSummary deck : deckService.deckSummaries()) {
        resBody.add(Json.object()
            .put("id", deck.id())
            .put("name", deck.name()));
    }
    return WebResponse.json(resBody);
});

app.post("/api/decks", req -> {
    String name = req.bodyJson(json -> json.asObject().getString("name"));
    Deck deck = deckService.createDeck(name);
    JsonObject resBody = Json.object()
        .put("id", deck.id())
        .put("name", deck.name());
    return WebResponse.json(resBody).status(HttpStatus.CREATED);
});

app.start(8080);
----

=== No reflection
The Spider Silk framework's own code uses no reflection.
There is no annotation scanning and no proxy generation at application startup, so startup is faster.
The framework's call stack is easy to follow, so the code is more traceable as well.
An application also compiles to a GraalVM native image more easily.

=== A minimal call stack
On its main call path, the handler, the framework adds only two stack frames above `HttpServlet.service`.
The other places the framework calls application code, such as filters, exception handlers, and streamed bodies, stay within four frames.
The fewer frames a stack trace holds, the easier the code at fault is to reach, so the code is more traceable.
This is a stack trace taken inside a handler.

[source,text]
----
java.lang.Throwable: where a handler stands
    at com.example.decks.DeckRoutes.one(DeckRoutes.java:15)  // the handler
    at net.benelog.spidersilk.AppServlet.dispatch(AppServlet.java:221)  // Spider Silk
    at net.benelog.spidersilk.AppServlet.service(AppServlet.java:128)  // Spider Silk
    at jakarta.servlet.http.HttpServlet.service(HttpServlet.java)  // the Servlet API
    at org.eclipse.jetty.ee10.servlet.ServletHolder.handle(ServletHolder.java)  // Jetty, from here down
----

=== A default stack with a minimal footprint
Spider Silk chose its default stack for fast startup and traceable code.
`spider-silk-core` includes Jetty as its web server and jte as its template engine by default.
With one dependency, an application starts with a server and a template engine in place.

==== Jetty
The default web server is embedded Jetty.
Of the three servers, Jetty provides server lifecycle management as its own features most completely.
With Jetty, therefore, less of this framework's code stands between the application and the server than with Tomcat or Undertow.
Jetty provides these features on its own:

* Jetty's own `stopTimeout` handles a graceful stop, `setStopAtShutdown` the shutdown hook, and Jetty's non-daemon threads keep the JVM alive.
* It runs without a working directory on disk.
* Sessions can be turned off with `sessions(false)`.

==== jte
The default template engine is https://jte.gg[jte].
jte compiles templates to Java source.
An expression such as `${deck.name()}` therefore runs as a compiled method call.
jte does not read model values by reflection, so it fits the no-reflection principle.
A precompiled template needs no compiler at runtime, so it works well in a xref:native-image.adoc[GraalVM native image] too.
In development, a `DirectoryCodeResolver` reading the source directory shows an edited template without a rebuild (xref:templates.adoc#production[Development and production]).

=== An extensible module structure
Spider Silk provides optional modules so that widely used technologies beyond the default stack can be used as well.
Every module depends on `spider-silk-core`, and core depends on none of them.

[cols="1,2,4,2",options="header"]
|===
| Category | Module | Contents | Dependencies

| Default
| `spider-silk-core`
| The framework itself.
The default web server is Jetty, and the default template engine is jte.
| `gg.jte:jte`, embedded Jetty (`jetty-ee10-servlet`)

.2+| Web server
| xref:tomcat.adoc[`spider-silk-tomcat`]
| Runs the same application on embedded Tomcat.
It suits an organization that already operates Tomcat, or an application moving over from Spring Boot.
| core, `tomcat-embed-core` 11.0.x

| xref:undertow.adoc[`spider-silk-undertow`]
| Runs the same application on embedded Undertow.
Undertow's graceful stop counts requests, so draining works on a virtual-thread executor too.
| core, `undertow-servlet` 2.3.x

.3+| Template engine
| xref:freemarker.adoc[`spider-silk-freemarker`]
| Renders with https://freemarker.apache.org[FreeMarker].
| core, `freemarker`

| xref:handlebars.adoc[`spider-silk-handlebars`]
| Renders with https://github.com/jknack/handlebars.java[Handlebars.java].
| core, `handlebars`

| xref:thymeleaf.adoc[`spider-silk-thymeleaf`]
| Renders with https://www.thymeleaf.org[Thymeleaf].
| core, `thymeleaf`

| WebSocket
| xref:websocket.adoc[`spider-silk-jetty-websocket`]
| Maps WebSocket endpoints beside the application's HTTP routes.
It is Jetty-only by construction, so it is a module named after Jetty rather than a method of `App`.
| core, `jetty-websocket-jetty-server`

| Testing
| xref:testing.adoc[`spider-silk-test`]
| The `WebTest` harness and `TestRequest`, for test scope.
It is a separate module, so the production jar carries no test code.
| core, and otherwise the JDK only (the servlet API compile-time only, as in core)

| Example
| `example-flashcard`
| A flashcard study application
| core, spring-jdbc, H2
|===

Routing, filters, status pages, JSON, templates, static files, SSE, multipart uploads, and sessions behave the same on all three servers.
The APIs of `TomcatServer` and `UndertowServer` follow `JettyServer`'s, so switching servers changes one line: the factory passed to `App.server(...)`.

The template engine is switched with `App.templates(...)`.
Switching engines leaves a handler's `WebResponse.template(name, model)` call as it is.

=== Development tool integration
Spider Silk provides tools for testing, API documentation, builds, and AI coding agents as separate modules and a skill, so that it fits the development tool ecosystem.

.Testing
* The `WebTest` harness of xref:testing.adoc[`spider-silk-test`] starts the application on a free port and hands over a client that keeps cookies.

.API documentation
* xref:openapi.adoc[`spider-silk-openapi`] turns the route list `app.routes()` answers into an OpenAPI 3.1 document.
Routes are plain data, so the module works without reflection.

.Build tools
* The xref:gradle-plugin.adoc[Gradle plugin] `net.benelog.spidersilk` carries the conventions for precompiled jte templates, Jib container images, and GraalVM native compilation.
* xref:maven-parent.adoc[`spider-silk-maven-parent`] provides the same packaging conventions as a Maven parent POM.

.AI coding agents
* The xref:agent-skill.adoc[agent skill] lives in `skills/spider-silk/` in the https://agentskills.io[Agent Skills] format, and guides an agent to use the framework as intended rather than by guessing.
Agent Skills is an open standard and the skill uses no feature particular to one tool, so Claude Code, Codex, Cursor, GitHub Copilot, and other AI agents read the same directory as it is.
The repository doubles as a plugin marketplace, so Claude Code installs it with two commands:

[source,subs="attributes+"]
----
/plugin marketplace add {project-repo}
/plugin install spider-silk@spider-silk
----

The repository is a Codex plugin marketplace as well, so Codex installs it with two commands too:

[source,subs="attributes+"]
----
codex plugin marketplace add {project-repo}
codex plugin add spider-silk@spider-silk
----
